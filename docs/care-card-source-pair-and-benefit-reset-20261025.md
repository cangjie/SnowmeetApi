# 购卡保存 500 与旧券卡清理（2026-10-25）

用户反馈：先添加装备，再添加捆绑次卡时返回 HTTP 500；确认新购卡后应清空装备原有券、会员卡选择。

## 实际原因及修复

线上日志确认 `CareCardSaleService.SaveDraftAsync` 的 UPDATE 触发 `CK_order_source_pair`。只读查询生产约束定义为：`order_source` 和 `source_order_no` 必须同时为空或同时非空。

单订单改造设置了 `order_source=care_card_single`，遗漏配套的 `source_order_no`。原 SQLite 回归库没有这个生产 CHECK，未覆盖此错误。

- 单订单保存时，将 `source_order_no` 设置为本订单自己的 ID 字符串；移除购卡时同时清空两列。此字段是来源标识，不创建第二条订单，`care` 和 `retail` 仍共用原 `order.id`。
- 购卡专项所有 SQLite 夹具加入相同的 INSERT/UPDATE 约束检查。新增回归先证明旧的单字段写法失败，再验证重复保存、移除、重新选卡和提交均成功。
- 前端确认选卡后清空全部装备的旧券对象/券码/券减免、旧卡 ID/名称/使用标记和绑板提示；保留装备、维修等信息，以购卡试算项目为准。
- 新购卡模式下，普通计价的迟到响应不能恢复旧券优惠；找回已提交或已发卡订单时只恢复结算展示，保留真实发卡核销引用。
- 服务端原有 `ApplyProjects` 在购卡保存事务内清除所有装备旧券卡引用，本次 500 修复后这一步可以成功完成。验证付款后只扣新发卡次数，旧卡次数和旧券使用状态不变。
