# 养护购卡共用一个订单（2026-10-25）

用户明确要求：养护和购卡共用一条 `order`，`care.order_id`、`retail.order_id` 都指向这个主订单，不能为购卡再创建第二条订单。

## 新单结构及金额

- 沿用原养护草稿的主键和养护订单号，`order.type=养护`、`sub_type=养护购卡`、`order_source=care_card_single`。不再创建零售主订单，也不再通过另一订单号关联养护。
- 单件装备、购买一张卡时：一条 `order`、一条 `care`、一条 `retail`。多件装备仍分别保存在 `care`，共用同一主订单；零售明细按实际售卡张数保存。
- `retail` 仅记录卡商品及其真实售价，保留原零售发卡来源。卡外项目、套餐补差和维修附加费保存在 `care.common_charge/repair_charge/discount`，新单不再额外生成“养护附加费用”零售行。
- 主订单金额为卡款加养护费用。例如卡款 0.01、维修附加费 0.01，主订单应付 0.02，支付流水也挂在这个订单下。
- 付款前安排继续暂存在 `retail.memo`；提交时冻结费用并检查试算变化；支付处理事务内核对快照、主订单金额、实收金额，再发卡、扣次、生成任务，最后清空临时安排。失败回滚、重复回调防重、取消养护返次、含卡订单禁退沿用原规则。

## 旧数据及客户端兼容

- `care_card_reception` 标记的既有两单结构仍按原关联继续支付、查询、重试业务完成和打印；不迁移或删除历史主订单和支付流水。
- 原接口路由、参数、响应字段保留。兼容字段 `careOrderId`、`retailOrderId` 在新结构中返回同一个 ID；旧数据仍返回各自原 ID。
- 普通养护、原有卡核销和顾客自助售卡不切换结构。
- `GetOrder` 对新结构同时加载养护及零售明细，并隐藏内部待付快照。两种零售查询入口均可查询本单的售卡记录；养护及全类型查询仍沿用原订单，同一全类型列表只出现一次。
- 养护草稿保存与购卡提交共用订单锁，保留服务端保存的卡明细及标识。旧客户端未带卡信息的负载不能清空快照；迟到的保存不能覆盖正式提交后的主订单。通用下单及零元核销入口不能绕过购卡提交与足额付款。
- 小程序的结算详情同时展示卡商品、卡款、养护费用和逐件项目；养护详情直接展示本单购卡内容。老两单的互查入口保留，新单不会显示成“关联另一张购卡单”。

不新增或修改数据库表、列，无结构 SQL，无生产历史订单迁移。
