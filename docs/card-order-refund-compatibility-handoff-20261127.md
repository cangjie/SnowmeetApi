## 服务端变化

- `Order/Refund/{orderId}` 对符合条件的含卡订单走新的整单退款流程；必须有员工权限和退款备注，并逐笔覆盖该订单的全部成功收款。卡和售卡明细必须一一对应，所有卡的已扣次数为零且无有效 `punch_card_used`。历史退款、挂账、收款金额不匹配和不支持的付款方式会被拒绝并要求核对。
- 在 SQL Server 的事务和应用锁下创建退款批次、分笔记录和卡快照，设置 `punch_card.refund_pending`。微信和支付宝按原付款单发起退款，现金、POS 机刷卡、京东收银视为线下退款登记；页面要求员工先确认线下实际退款，服务端应重点检查其他调用方是否遵循该前置条件。
- 渠道结果未知或部分退款成功时保持全部卡冻结；所有分笔确认成功后设为已退款并解除待处理标记；全部分笔明确失败后恢复卡。微信主动查询和成功回调、支付宝未知结果查询以及重复请求的状态合并均有改动。处理中退款不计入订单已退款金额，但相关分笔仍需占用退款额度，防止重复退款。
- 养护选卡和核销、租赁选卡及优惠结算、会员后台资产汇总会排除退款冻结卡；会员卡列表和详情接口增加 `isRefundPending`。顾客自助退卡入口提示联系门店或退款处理中，不开放单张卡绕过整单退款。
- 当前实现明确拦截旧的“养护单关联零售单”结构；租赁类型的含卡订单也不支持此整单退款入口。普通非含卡订单沿用原退款分支。不要把这些限制误判为已支持。

## 数据库和接口兼容性

生产库已添加 `punch_card.refund_pending bit NOT NULL DEFAULT 0`、`payment_refund.card_refund_batch_id int NULL`、`payment_refund.card_refund_state varchar(20) NULL`、`card_order_refund_batch`、`card_order_refund_card` 和相应索引。生产变更时 78 张卡的冻结标记均为 0，两个新表为空。其他测试数据库须先建立等价结构；本仓库的 `docs/sql/2026-11-27_card_order_refund_schema_DRAFT.sql` 仅供参考，本文件整体未作为单个 SQL 批次验证，不要直接用于生产。

订单详情中 `careCardSale` 新增 `canRefund`、`refundStatus`、`refundMessage`、`canRetryRefund`；卡列表及详情增加 `isRefundPending`；退款分笔增加 `card_refund_batch_id` 和 `card_refund_state`。请核对旧版小程序、管理后台、报表及其他 API 消费者对新增字段和退款金额口径的兼容性。
